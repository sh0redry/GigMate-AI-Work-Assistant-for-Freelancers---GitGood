# Source-bound AI clarification

The reviewed text extraction call may also produce a clarification assessment.
It judges date, start time, end time, duration and address as known, missing,
ambiguous or explicitly deferred. This is additional semantic reasoning in the
existing call, not a separate paid model request for each field.

The independent version 1.0.0 assessment schema is generated by
`scripts/export_contracts.py` into
`contracts/ai/clarification-assessment.schema.json`. A nullable JSON column on
`proposals` stores the assessment and its server-captured order basis (migration
`0024_context_clarification`). Existing rows remain usable and `TimedSchedule` still requires both ends.
No incomplete interval can enter the calendar through this feature.

Every non-missing assertion requires current authorized customer message IDs,
revisions and verbatim evidence. The model selects the unresolved items, their
order and a concise/friendly tone. The server verifies exact coverage and fills
quoted facts into bounded customer wording. This makes the AI's question choice
reviewable while preventing arbitrary new facts or execution claims in that reply.
The old merchant-summary `draft_text` remains a different purpose.

Only a matched order or an explicitly adopted new-order suggestion can use an
assessment. Complete/manual facts take precedence; a partial amendment can ask
for its missing duration without replacing the original confirmed appointment.
Clarifications remain ordinary immutable, version-bound approval actions and
require the existing explicit sending permission and final send command.
Recognizing "I will provide it later" suppresses immediate questioning; it does
not apply a formal deferral or create a follow-up task without a merchant command.

Recent text remains bounded. Up to three explicitly linked orders may additionally
contribute at most 5000 UTF-8 bytes of previously assessed facts and evidence
snippets, revalidated against current owned source revisions and consent. Every
source must have a durable receipt after the conversation's latest consent
boundary. Revocation and reauthorization advance that boundary; previously
stored text does not become model context automatically. The migration conservatively
sets existing conversations' boundary to their current context version, retaining
their messages and orders while requiring newly accepted input for this feature. A model
may reuse this evidence only for the selected existing order, never for a new or
different job. New customer messages require fresh analysis. Own API send echoes
can preserve the prior fact basis without creating recursive model calls.

Invalid, absent, stale or unassigned assessments use the existing template/manual
review behavior. They never authorize a send, auto-retry an unknown paid outcome,
or confirm a booking. Quoted evidence proves source identity, not semantic truth;
the model can still misunderstand negation or intent, so merchant review remains
necessary. Quality improvements must be measured on comparable cases, not inferred
from passing mocked tests. Keys and connector credentials never enter model input.

Regression tests live in `apps/backend/tests/test_clarification.py`; PostgreSQL,
migration/data-preservation checks and bounded synthetic vendor acceptance are
recorded with their actual results in the implementation status.

This mainline migration starts at `0023_agent_drafts`, independently of the
private finals migration chain. Never edit applied finals revisions or run this
mainline upgrade blindly against an existing finals database; reconcile those
histories separately before moving a finals installation onto main. No activity
tables, registration rules, seeded scenarios or reset hooks are required.
