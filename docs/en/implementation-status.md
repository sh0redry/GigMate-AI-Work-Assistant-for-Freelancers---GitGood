Stacked on the status-command PR. Design: 方案 §4.5 (send after approval, cancel plans, view results), §6.2 (`sendText` after server-side approval check, idempotent record, unknown outcomes checked), §7 (approval binds exact content and versions; outdated approvals cancelled); Issue #29 §1.

## Work-order creation and key-items rule (role C) — 2026-10-13

Stacked on PR #22. Adds `POST /work-orders` (`CreateWorkOrderCommand`) and the contract section 3 key-items rule.

- **Creation:** merchant creates an order from an owned, allowlisted conversation; `summary` 1–120 characters (blank rejected). Each given value names the customer message(s) that said it (`schedule_sources`, `address_sources`); sources must be current revisions in this conversation and messages the customer sent (`direction: incoming`); the merchant's own reply or an API send echo returns 422. A blank address (spaces or tabs only) returns 422 and never counts as confirmed. Missing values stay `missing`. A timed schedule must be in the future and must not overlap a confirmed appointment (409 `SCHEDULE_CONFLICT` with `work_order_ids`). Without `confirm_additional_order`, a conversation with an open order returns 409 `OPEN_ORDER_EXISTS` with those IDs. Creation is serialized per account and idempotent; an audit record is written.
- **Key-items rule:** an order is `confirmed` only when a timed schedule and an address are both confirmed **by the merchant and by the customer**. Confirming a proposal whose `customer_confirmation` is not `confirmed` (for example a relative date the provider resolved) writes the value but keeps the field `proposed`, so the item stays open; a confirmed order whose key item now awaits the customer, or whose time is replaced by a date without a time, returns to `pending_confirmation`, its calendar entry becomes tentative and its generated preparation task is cancelled (previously the date-only case returned 500). Values the merchant enters at creation cite the customer's own message and count as customer-confirmed; a date-only value stays `proposed`. A timed schedule alone blocks the slot (formal calendar entry) but the order stays pending with no preparation task; a date-only schedule (at creation or through confirm) is a tentative entry and is never conflict-checked (previously confirming a date-only proposal failed). Orders confirmed before this rule (seed data without address) are not demoted.
- **Open-item drafts:** whenever an order is created or confirmed and is still `pending_confirmation`, one `send_text` draft (trigger `open_items`, reason codes in `open_items`: `missing_schedule`, `verify_schedule`, `missing_time`, `missing_address`, `verify_address`) asks only for the open items and echoes unverified values, e.g. 「你好，想跟你确认一下：你说的是 10/17 吗？几点方便？见面地址是？」. It replaces older unsent drafts (`superseded`); the last confirmation closes it (`resolved`). After a new message it follows the existing hold/reissue rules; reissue rebuilds the questions from the order's current open items (409 if nothing is open). Trigger identity is `open_items:<order>:v<version>:<codes>`, or `open_items:<replaced action>:r<context>:<codes>` for a reissue round, so repeated rounds never collide and the value stays within the 128-character column.
- **Conflicts:** cancelled or completed orders no longer occupy their time slot.
