## 1. 起点与总体目标

扫码、session 绑定、会话选择和首次历史同步的产品/技术路径见[WhatsApp 连接与消息获取](whatsapp-connection-flow.md)，对应 A-02/A-03 的开发与验收。

当前基线是 v0.2：FastAPI + SQLAlchemy/Alembic + PostgreSQL，单仓库模块化后端和独立 Worker。已实现开发账号认证、允许会话的 Replay 新建/修改/撤回、Inbox/Job、版本校验、固定抽取桩和内部日程确认。可选本地 WAHA 持久接入/监控及真实文字变更已经验证；真实通用 AI、生产鉴权、发送审批/outbox/核对尚未完成。见[当前能力与交接](role-a-waha-handoff.md)。

2026-10-06 计划：按用户要求，官方 Cloud API 暂停，不纳入当前计划。下一步为 E 的 A-03 统一独立评审与人工缺口核对；后续获授权的 WAHA 页面/真实处理/批准执行批次分别依赖 D/B/C，不自动进入发送开发。

目标链路：Replay 或 WAHA → 来源鉴权与可信归属 → 白名单 → 标准事件 → PostgreSQL 原子接收与持久任务 → Worker → 提议与业务服务。连接状态进入独立持久状态及账号隔离接口；未来发送链路由 actions 审批后通过 adapter 执行。

先读[架构](../en/architecture.md)、[ADR](../en/adr/README.md)、[契约入口](../../contracts/README.md)、[API 约定](../../contracts/api-v1.md)与[开发命令](../en/getting-started.md)。历史启动计划不是当前完成依据。

## 2. 批次开发规则

每次先定义里程碑、任务清单、依赖、排除项和统一验收标准，然后一次完成尽可能多的相关任务。顺序为：契约与设计 → 实现与迁移 → 测试和故障修复 → 集成与文档 → 一个完整验收包。

下述批次是依赖边界，不是要求用户逐项验收。若账号、契约和环境齐备且在同一已授权里程碑内，可以把相邻批次合并完成后统一验收。开发过程可连续多次编辑、测试和汇报，不在每个子任务末尾停下来等确认。不得为了扩大批次跳过安全、版本、测试或评审要求。

发现外部阻塞后，继续完成可独立开发的 adapter、合成测试、持久化、接口和文档；统一交付已完成部分与阻塞列表。需要账号/环境的验证仍记为未完成，不能拿 mock 冒充真实通过。未来能力需获授权后实施，本次只交付文档。

## 4. 批次 A-01：稳定事件契约与回放异常基线

2026-10-02：在用户“新增文件、不改共享实现”的限制下，独立适配、合成语料、测试和本地演示已交付。实际证据、映射规则及共享集成待办见[A-01 统一验收](role-a-stage1-acceptance.md)；不代表整条真实接入链路完成。

目标：其他成员能够依赖同一输入结构开发，不受真实接入影响。

任务：

1. 盘点五类 schema 事件与当前三类接入实现，形成支持矩阵；区分有契约、可接收、可消费和真实验证。
2. 明确账号/会话映射、事件身份与消息身份、revision、时间、source/direction 和 payload；不靠到达时间生成去重身份。
3. 与 B/C/D 确认下游输入、错误行为和兼容性；破坏性变更有版本及迁移说明。
4. 补合成样例及 manifest，完善可重放工具，覆盖修改、撤回、非法字段、重复、身份冲突、版本缺口及跨会话消息 ID。
5. 与 E 编写正常/异常矩阵及可重现步骤；复用现有测试，按缺口补有意义的用例。
6. 核对接收事务：Inbox、消息版本、context_version、提议失效和 Job 同成同败，提交前不确认成功；失败不留下业务内容或半套任务。

交付：事件说明、样例、支持矩阵、回放工具/测试、契约变更清单和中英文文档。统一验收：合法输入进入持久任务，非法/越权输入不写业务内容，重复不新增，冲突明确，旧内容不能继续生成可确认提议。领域确认规则仍由 C 负责。

## 5. 批次 A-02：真实接入适配与安全入口

依赖：A-01；授权的非关键测试账号、可用 WAHA 环境；完成当前协作门槛的适用事项。先做最小能力探测，再据结果实现，不从供应商宣传推断能力。

任务：

1. 实测并固定 WAHA 版本、引擎及部署配置；记录文字、编辑、撤回、回执、历史查询和重连补取的支持情况。
2. 用真实测试结果确定供应商 ID 与内部 UUID 的持久映射、重复推送身份、消息版本规则和缺失字段策略。重复的接收时间不得改变事件语义摘要；确认现有全事件 digest 在真实重投时的兼容性。
3. 新增 adapter：供应商输入转换为严格标准事件；限制大小/类型；不支持的媒体或事件有明确处置，不误当文字。
4. 新增供应商 Webhook 入口与独立鉴权：使用该固定版本实际支持的密钥/签名机制；从服务端配置解析账号/session；检查授权和白名单后才存内容。若支持签名时间戳等机制，再设计对应重放防护。
5. 配置凭据仅在服务端；管理地址不暴露给前端；请求/异常日志不得打印正文和凭据。
6. 对错误重投、连接超时和数据库提交失败制定响应规则，与实测供应商重投策略对应；HTTP 成功只意味着已提交接收。
7. 保留 Replay 的无真实账号开发路径，完成 mock/合成集成测试和独立真实接入验证。

交付：版本/能力报告、adapter、Webhook、安全配置、必要的新迁移、端到端测试与脱敏验证结论。统一验收：真实允许的文字进入持久链路；伪造来源/跨账号/非白名单被拦截；重复不重复建任务；重启后映射和数据保留。不支持的编辑/撤回能力明确列为限制，不写成通过。

## 6. 批次 A-03：连接状态、可观测性与可靠恢复

依赖：A-02 的平台能力结论；可与 A-02 同一完整批次交付。

任务：

1. 定义并持久化 connector/session 与账号关系、connected/connecting/disconnected/failed 状态、状态来源时间、最后成功同步、新鲜度和安全错误码；新增模型/迁移。
2. 处理重复、延迟状态通知和服务重启；状态顺序必须依据供应商能力或核对结果，不能让迟到旧通知覆盖当前状态。
3. 扩展 connection-status 源模型/接口并重新生成契约及类型；与 D 完成回放/真实模式、失联/过期状态展示，不把 API 健康等同于聊天连接健康。
4. 记录接收量、重复/拒绝量、接收至处理耗时、待处理积压、失败任务、过期租约和断线时长；阈值根据实测负载设置，不承诺未经测试的性能指标。
5. 根据实测查询/补取能力建立断线恢复或人工核对流程。补取同样通过鉴权/白名单/去重/来源规则；不支持补取时明确漏消息风险及操作路径。
6. 与 C 验证并发领取、同会话处理、账号锁顺序、任务租约和重试上限；续租如有需求必须防止失去租约的旧 worker 提交结果。
7. 与 E 注入接收时数据库故障、worker 数据库故障、提交后响应丢失、worker 崩溃、连接断开、重复补取和乱序版本，检查恢复无半写/重复业务副作用。

当前 Worker 对账号加锁，范围比单会话更粗；不要把计划中的精细并行描述为已实现。当前回放拒绝 revision 缺口；真实乱序要设计持久等待/查询核对或人工复核，不直接按到达时间覆盖。

交付：状态存储/接口/展示、指标与排障、恢复策略、PostgreSQL 故障测试及证据。统一验收：状态隔离且有新鲜度；重启可恢复；两 worker 不重复提交；失败有限；遗漏可核对或明确复核；日志无敏感数据。

## 7. 批次 A-04：与审批发送链路衔接

这是后续里程碑，不属于当前回放扩展默认范围。依赖 C 的 action 快照、审批、版本复核、事务 outbox、取消和结果核对服务；不能由 A 先加“任意发消息”接口绕过这些规则。

任务：

1. 根据固定平台实测实现发送/查询能力，将明确未提交、已受理、已送达与结果未知分别映射，不把供应商受理当客户确认。
2. 提供连接可用性和错误分类；C 在 dispatch 前复核授权、归属、连接、取消、到期以及工单/上下文/action 版本。
3. 标记 API 发送回显：更新上下文，但不循环回复，不追溯取消已派发发送；后续排队动作仍需当前上下文。
4. 可能提交后的超时进入 result_unknown 并核对，不盲目重发；仅确定未提交的失败才按有界策略重新检查后重试。
5. 与 C/E 覆盖断线、撤销授权、输入与派发竞争、回显、结果未知和重启恢复；明确本地串行不能覆盖尚未送达的远端消息，不承诺外部 exactly-once。

交付：adapter、能力与错误语义、合成异常和授权真实验证。统一验收以审批执行整条链路为单位，不拿单次发送成功替代。

## 9. 统一验收流程与命令

按[开发入口](../en/getting-started.md)使用 `.venv` 和锁定依赖。文档批次执行 baseline；代码批次按影响执行 Ruff check/format、生成漂移、baseline、迁移 upgrade/check、pytest；改 API/前端时执行 check:api、format:check、build；运行环境中验证 smoke、重启、故障恢复。

```powershell
.venv/Scripts/python.exe scripts/check_baseline.py
.venv/Scripts/python.exe -m ruff check apps/backend scripts/export_contracts.py scripts/smoke_replay.py
.venv/Scripts/python.exe -m ruff format --check apps/backend scripts/export_contracts.py scripts/smoke_replay.py
.venv/Scripts/python.exe scripts/export_contracts.py --check
.venv/Scripts/python.exe -m alembic -c apps/backend/alembic.ini upgrade head
.venv/Scripts/python.exe -m alembic -c apps/backend/alembic.ini check
# 按开发入口设置 PYTHONPATH 和隔离测试 PostgreSQL 地址后执行：
.venv/Scripts/python.exe -m pytest apps/backend/tests -q --basetemp=local-data/pytest
# apps/web 目录内：npm run check:api / npm run format:check / npm run build
```

命令是未来批次检查清单，不是本次执行结果。缺依赖应明确失败；SQLite 结果不得证明行锁。pytest 的 basetemp 是可替换内容的测试专用目录，不指向用户文件或工作台数据。不要用真实聊天验证公开 fixtures。

统一验收包采用以下清单：

- 批次 ID、授权范围、基线版本、完成/阻塞/未开始任务。
- 行为变化、端点支持矩阵、契约版本、迁移和配置步骤。
- A-E 用例的实际命令/结果、数据库类型和版本、真实验证的能力限制。
- 重启/故障恢复证据、缺陷修复与必要复测、评审影响清单。
- 中英文完成记录、剩余风险与下批依赖；未执行项明确说明原因。

开发者先完成自检和修复，再由 E 组织一次批次验收；跨模块代码仍按现有规则独立评审。验收失败就在当前批次修复，针对变化复测；已通过且未受影响的检查不为形式反复运行。只有验收项实际满足才记录完成。未经请求不提交、不推送、不部署外部发布。
