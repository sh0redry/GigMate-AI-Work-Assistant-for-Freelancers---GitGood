# A 的职责：消息接入、鉴权、事件队列与连接监控

更新：2026-10-02。本文明确用户承担的 A 角色范围，不代表其他成员已实际认领模块。当前实现为 v0.2 合成消息回放骨架。

A 负责把外部聊天变化转换为可信、稳定、可追踪的事件，可靠地交给后续处理，并让团队看见接入是否正常。交付重点是“收到的是什么、属于谁、有没有重复、有没有丢失、连接是否可用”。完整开发顺序见[技术开发演进](role-a-development-roadmap.md)，英文对应说明见[Role A](../en/role-a-responsibilities.md)。

## 1. 职责与现状

用户如何扫码、选择允许会话，以及 WAHA 如何获取实时/历史消息，见[WhatsApp 连接与消息获取](whatsapp-connection-flow.md)。

| 职责 | 具体工作 | 当前实现与待开发范围 |
| --- | --- | --- |
| 消息接入 | 维护 Replay；实测并固定 WAHA 版本/引擎；转换新建、修改、撤回、回执和连接事件 | Replay 的文字新建/修改/撤回已实现；真实 WAHA adapter、回执和连接事件处理待开发 |
| 接入鉴权 | 验证 Webhook 来源；服务端解析账号/会话归属；先检查授权和会话白名单，再存内容或调用模型 | 开发登录、CSRF、账号隔离和白名单已有；生产登录、真实 Webhook 密钥/签名鉴权待开发 |
| 稳定事件结构 | 维护事件 schema、平台字段映射、身份/版本规则、正反样例及能力说明 | wire 0.1.0 已定义五类事件；定义存在不等于服务已支持 |
| 可靠接收与队列 | 原子保存事件、消息版本、上下文版本和任务；处理重复、冲突、故障和恢复 | Inbox/Job/独立 Worker 已有；真实供应商身份映射与乱序核对待验证 |
| 连接监控 | 持久保存连接状态和同步进度；提供账号隔离的状态接口；记录安全日志和告警依据 | 当前接口仅返回 synthetic_replay、replay、live_connected=false；不是实时连接监控 |
| 接入基础环境 | 维护接入相关 Compose、服务端配置模板、启动排障及恢复说明 | 复用现有单仓库、模块化后端、独立 Worker 和 PostgreSQL；不先引入新队列服务 |
| 与 E 异常测试 | 提供可重放输入、故障注入方法、错误码和证据，修复接入问题 | 部分回放异常已有测试；真实连接、Webhook、发送回显仍需后续验收 |

## 2. 优先交付：稳定事件结构

从[现有事件契约](../../contracts/events/message-event.schema.json)开始，不另造一套字段。事件 schema 独立版本化；领域模型以 `contracts.py` 为准，domain/OpenAPI/前端类型通过工具生成，不手改生成文件。

| 字段 | 含义与责任 |
| --- | --- |
| schema_version / event_type | 格式版本及事件类别，明确支持和不支持的种类 |
| event_id | 同一次事件重投保持稳定；平台没有稳定 ID 时，先实测，再制定持久映射规则 |
| account_id / session_id / conversation_id | 账号、连接和会话；真实接入通过可信服务端映射确定，不能相信请求体自报归属 |
| provider_message_id / payload.message_id | 外部消息身份与内部消息身份；不混用事件 ID |
| message_revision | 同一消息的版本；新建、修改、撤回保留来源链 |
| occurred_at / received_at | 平台事件时间与接收时间；UTC RFC3339，尾部 Z；不以接收顺序猜测真实版本 |
| direction / source | 收入/发出、应用/API/回放来源；为后续处理自发消息回显提供依据 |
| payload | 对应事件类型的严格内容结构；未知业务值保持缺失，不凭空补全 |

例如，一条消息先发出、后修改、再撤回：消息身份相同，但这三次变化的事件身份不同，来源版本逐次推进。重复推送同一次变化才是去重对象。回执不能被误当成新客户消息或客户确认。

交付应包含：字段说明、供应商到标准事件的映射表、能力矩阵、每类正例/非法例、重复/冲突/乱序处理规则、兼容性影响、自动校验和下游消费示例。严格客户端需要一起协调；破坏性字段或语义变更走主要版本/API 迁移。

## 3. 队列与鉴权的工作边界

处理顺序：验证来源 → 解析归属 → 检查账号授权和会话白名单 → 校验标准事件 → 事务内去重、保存消息版本、推进 context_version、使旧提议失效并创建任务 → 提交后确认接收 → Worker 处理。

未授权或未入白名单的业务正文不得先进入数据库、日志或模型。连接凭据只在服务端，不能交给前端或模型。日志保留 ID、阶段、耗时和稳定错误码，不记录完整消息、地址、令牌、QR 或 session 文件。

队列使用现有 PostgreSQL 表。A 与 C 统一事务、唯一约束、租约、重试和版本规则。当前 Worker 使用 SKIP LOCKED、30 秒租约、失败后三次尝试上限和退避；这些是当前实现参数，后续调整须带验证。SQLite 无法证明 PostgreSQL 锁行为。

真实乱序事件需要可靠核对机制；当前回放对非连续 revision 返回 VERSION_CONFLICT，不具有自动乱序修复能力。接收成功只说明已持久接收，不代表 AI 已完成、工单已确认或消息已发送。

## 4. 与其他角色的交接

| 对接角色 | A 提供 | 对方负责 / 共同确认 |
| --- | --- | --- |
| B：AI | 允许处理的消息、来源版本、上下文版本、稳定输入与错误说明 | 抽取、提示词和评测；AI 只输出建议/草稿 |
| C：业务与架构 | 去重、可靠任务、可信归属、上下文变化及连接状态 | 业务模型、确认/审批/发送规则；共同评审共享契约、迁移和事务 |
| D：前端 | 账号隔离的连接状态和业务错误；声明新鲜度与支持能力 | 状态展示和用户操作；前端不调用连接器管理接口、不持有凭据 |
| E：验收 | 合成输入、故障操作、可重放路径、定位 ID 和修复证据 | 组织异常用例、缺陷、用户验收与演示材料；一起确认预期 |

A 不直接确认工单、修改正式日历或凭 AI 草稿外发。一个会话可关联多个工单，归属不清由下游进入人工复核。后续发送时，A 提供 adapter 的能力和结果信息，C 负责审批绑定、事务 outbox、执行前复核及结果核对。

## 5. 与 E 必测的异常

| 情况 | 预期 | 当前覆盖边界 |
| --- | --- | --- |
| 重复事件 / 同 ID 不同内容 | 前者不重复建记录和任务，后者拒绝冲突 | 有回放测试 |
| 未登录、CSRF、跨账号、非白名单、撤销授权 | 拒绝，未授权内容不落库/不调用 AI | 部分开发鉴权/回放测试；真实 Webhook 待测 |
| 修改、撤回和旧内容任务 | 保留来源版本；旧提议不可继续确认 | 有撤回和过期上下文测试；真实乱序待测 |
| Worker 崩溃、租约过期、并发领取、持续失败 | 可恢复；不重复写提议；有限失败重试 | 已有测试；并发锁必须跑 PostgreSQL |
| 数据库不可用 | 不虚报接收成功；恢复后任务继续 | 已有 Worker poll 故障测试；接收事务故障需补完整用例 |
| 断线、重连、状态通知重复或延迟 | 状态可靠，恢复后的遗漏/重复可核对 | 真实实现待开发 |
| API 自发消息回显 / 发送结果未知 | 不循环回复；已发结果不倒退；未知结果不盲重发 | 外发链路待开发，当前不是通过项 |

测试输入用合成数据。真实接入验证需要独立授权的测试账号和本地私有证据，仓库只保留脱敏结论与合成复现。

## 6. 开发与验收方式

现在及后续开发，优先在已授权里程碑内一次完成尽可能多的相关任务，形成可运行的完整批次，再统一验收。不要每完成一个文件或小任务就要求用户验收。批次应同时覆盖实现、迁移、契约/类型生成、正常/失败测试、配置和中英文文档。

开发中自行运行必要检查、修复失败并报告进展；统一验收不意味着把自动检查推迟到最后。遇到测试账号/凭据等外部依赖时，继续完成不受阻的工作，交付清单明确阻塞项，不能写成真实接入通过。大批次仍保持模块清晰、变更可审查，不扩展未授权里程碑，不省略独立代码评审，也不自行提交或推送。

验收包包含：批次任务表、行为变化、契约/迁移说明、实际命令与结果、异常矩阵、恢复证据、已知限制及剩余任务。完成记录同步写入[中文进度](progress.md)和[英文状态](../en/implementation-status.md)。
