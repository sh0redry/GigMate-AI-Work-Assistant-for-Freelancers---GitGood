## 可以发送什么

| 类型 | 本批范围 |
| --- | --- |
| 文字、链接 | 最多 4,096 字符；不让 WAHA 自动抓取链接预览 |
| 图片 | JPEG、PNG、WebP，可附说明文字 |
| 文件 | PDF、UTF-8 TXT/CSV、DOCX/XLSX/PPTX；其他允许上传的文件也可作为普通附件 |
| 普通音频 | Ogg、MP3、WAV、M4A，按附件发送 |
| 语音气泡 | Ogg 且包含 Opus 头；与普通音频分开，不自动转换 |
| 视频 | MP4，校验容器签名；WEBJS 需要 Google Chrome，不自动转换 |
| 贴纸 | WebP，不自动转换 |
| 位置 | 用户明确填写经纬度及名称；空坐标不会变成零 |
| 联系人 | 明确填写姓名及含国家码的号码，最多 10 位联系人 |
| 投票 | 问题、2–12 个不同选项、明确选择是否允许多选 |
| 表情回应 | 选择已载入、属于本会话且未撤回的消息；留空表示移除回应 |

除表情回应外，都支持引用回复本会话的消息。单文件上限 20 MiB；TXT/CSV 上限 1 MiB，必须是 UTF-8。扩展名、声明 MIME 与签名必须符合范围。Office 文件只作为附件传送，不解压或执行。签名检查不是完整解码、编码器认证或病毒扫描；自动测试里的简化头部也不能证明手机一定能播放。

一个任务对应一条消息或一个文件。相册、多文件原子批次、转发、编辑已发送文字、删除消息、频道/动态、按钮/列表及转码尚未接入。表情接口成功不等于产生一条新消息，也没有虚构送达/已读回执。

请求与字段已核对[固定版本源码](https://github.com/devlikeapro/waha/blob/2026.9.1/src/api/chatting.controller.ts)和[官方发送说明](https://waha.devlike.pro/docs/how-to/send-messages/)；表情回应使用 PUT。执行前检查 WAHA **2026.9.1 / WEBJS**、正常登录、预期签名回调及 `tagsEventsOn=true`。不匹配时在提交前失败，不自动改远端配置。能力接口表示我们实现了适配器，不表示所有类型已经通过真实手机验收。

真实 WEBJS 发送可能返回 SDK 的 ID 对象，本批读取其 `_serialized`（也支持已序列化字符串），仍检查接收会话。表情方法返回空值，成功的空 HTTP 响应只记录接口接受；SDK 找不到目标时可能静默跳过，因此必须核对手机，不能当成已经应用/送达。视频在 Chromium 环境会被引擎拒绝，本批提交前检查 Google Chrome，缺失时明确报 `WAHA_SEND_VIDEO_REQUIRES_CHROME`，不会发出。依据[引擎源码](https://github.com/devlikeapro/waha/blob/2026.9.1/src/core/engines/webjs/session.webjs.core.ts)及[固定 SDK](https://github.com/devlikeapro/whatsapp-web.js/blob/fork-main-2026-06-26/src/Client.js)。

## 三种模式的区别

**手动：**填写、上传、保存草稿；此时不会发送。核对最终正文、聊天、附件名及 SHA256，再点击“确认上述内容并发送”。修改输入会准备新草稿，不会偷偷修改已批准内容。

**Agent 润色后：**B 提供建议稿，用户可以修改，再核对最终快照并批准。页面目前允许粘贴建议稿，明确显示 B 尚未接入真实润色模型；选择这个模式不是已调用模型的证明。A 没有写一个假模型来冒充 B。

**Agent 自动：**商户先批准一个会话、一份固定内容、有效期和次数上限。B/Agent 的可信服务端调度器可以提交相同内容及政策 ID，无需每条再点击。后端校验接收人、正文、附件/hash、引用来源、当前上下文和可选工单版本，并在同一事务中预留次数、批准并排队。政策最多有效 7 天、最多 100 次；页面默认 24 小时、5 次。不同文字或附件不能借用旧政策；需要自由生成或业务归属不明确的内容转人工。

页面“按已授权政策提交”用于联调这个通道，**不会启动后台 Agent**。真实生成、自动触发判断、定时调度仍由 B/编排服务接入。模型只能提出内容，不能取得商户 cookie、CSRF、WAHA 密钥、地址或存储路径；工具调用身份及持久请求键由可信服务端处理。

## ABCDE 如何接着开发

- A：附件上传/存储、多类型 WAHA 适配、授权、审批快照、持久队列、回执和恢复。
- B：真实润色/生成，保留来源与未知信息，判断建议是否符合固定政策。保存原命令及请求键；丢失响应不能换键重发。
- C：工单关联、版本和业务来源。发送命令可带 `work_order_id` 与 `expected_work_order_version`，A 校验归属、关联和版本。未关联工单的消息只是商户通信，不是自动确认预约。一个会话不能猜成一个工单；发送成功或客户已读都不写工单、日历，也不等于客户确认。本批 `WahaSendAction` 是已实现的 WAHA 网关，不要把旧 `ApprovalAction` 规划模型当成已有通用执行服务。
- 后端也固定**所有已关联工单的版本**，不猜测目标；因此即使消息上下文未变化，C 单独修改工单或关联也会使旧发送/固定政策失效。引用规范文字时还绑定实际最新修订，并检查规范消息的撤回状态，不只看快照。
- 涉及业务的自动政策可在商户批准时明确绑定 `work_order_id` 与 `expected_work_order_version`。自动提交必须保留这个目标/版本；政策未关联时也必须保持未关联，B 不能悄悄把已批准的消息改标到另一个工单。
- D：使用生成类型，展示最终快照、明确批准和结果未知流程。
- E：独立检查权限、并发、异常及真实账号行为。

## 接口、状态与恢复

接口前缀 `/api/v1/connectors/{connection_id}/sending`。所有接口由服务端确认当前账号归属；所有 POST 校验登录、来源及 CSRF。读取授权不会自动获得发送授权。默认关闭 `WAHA_SEND_ENABLED`；附件还需原有私有媒体存储。

上传正文为 `application/octet-stream`，使用 `X-File-Name`（UTF-8 文件名百分号编码）及 `X-File-Mimetype` 请求头，文件名不进入访问日志 URL。收流前检查身份，限制 30 秒/20 MiB；收完再检查登录、授权和配额并串行落库。接收上传及远端回执 GET 期间不占账号业务修改锁，原有其他修改接口的默认鉴权锁保持不变。

| 接口 | 用途 |
| --- | --- |
| GET capabilities / permission / context/{chat_id} | 查询功能、发送授权及当前版本 |
| POST permission | 对白名单会话单独授权及设置有效期；撤销不依赖 WAHA 私有配置或功能开关 |
| POST uploads；GET uploads/{id}/content | 有大小限制的原始字节上传、私有 hash 校验预览/下载；不接受任意远端 URL |
| POST drafts | 必须携带 Idempotency-Key；保存人工草稿，或按完全匹配政策直接排队 |
| GET requests/{key}；POST requests/{key}/cancel | 查原请求；尚未落库的取消会留下记录，阻止晚到的相同请求创建任务 |
| GET actions / actions/{id} | 分页查看任务、最终快照及回执；列表可按会话过滤 |
| POST actions/{id}/approve / cancel | 检查动作版本，批准或在提交前取消 |
| POST actions/{id}/reconcile | 只按已返回的准确消息 ID 查询回执，绝不再次发送 |
| POST actions/{id}/review-unknown | 商户明确承认可能已发送并填写核对说明；原任务仍未知，只解除后续独立任务阻塞 |
| POST policies；GET policies；POST policies/{id}/revoke | 批准固定内容、有效期、次数及撤销政策 |

一条持久记录同时承担不可变审批快照和事务 outbox。它绑定接收人、内容/附件信息/hash、引用来源、动作版本、连接/授权/上下文版本、可选工单版本及有效期；模型建议与商户批准分别记录。

worker 先保存 `preparing`，在业务锁外做 GET 检查，再重新校验、提交 `dispatching`，最后在锁外只调用一次发送 POST/PUT。**提交 dispatching 是本地开始外部执行的边界。**在这个边界前已提交的新消息/撤销会阻止发送；之后无法撤回正在进入执行的远端请求，也无法保护尚未送到本系统的远端事件。准备阶段租约可恢复；提交阶段租约过期只转“结果未知”，不重复发送。不可变的提交标识允许保留原尝试晚到的成功响应，即使租约已被回收，也不授权第二次提交。提交后的意外失败一律保守处理；检查阶段失败则没有发送。不能承诺外部 exactly-once。

新增消息、编辑、撤回会使未发送的草稿/队列失效。API 发出的文字回流会推进上下文，但不会再次调用提取；没有正文的结构化 API 回流只记录观察。已进入发送的任务保留结果，之后的任务必须核对新上下文。回执只按准确返回 ID 关联，状态不倒退。

没有返回 ID 时，聊天里一条相同文字不一定就是本次发送，查询不到也不证明没发送。默认阻塞该会话后续任务；人工核对不能把未知改成已送达/业务确认，也不退还政策次数。浏览器仅保存会话范围的请求标识，不保存正文、文件或凭据；重新打开页面后先查原记录。查不到时仍待核对，直到明确取消原请求、建立后端取消记录。

固定版本 WAHA 的 `source` 位于消息 payload 内。本批接收/规范化已覆盖这一真实结构，并兼容旧的顶层合成测试字段；两处声明冲突、来信冒充 API 来源时拒绝。默认 app 来源不改旧去重身份；这是经过签名的来源信息，不是前端标记。参见[事件字段](https://waha.devlike.pro/docs/how-to/events/)。

本批限制：每连接最多 100 个未完成草稿/排队任务；UTC 每日最多 100 次提交，至少间隔 5 秒；保留上传上限 100 MiB。上传文件 24 小时过期，维护删除本系统拥有的到期文件及过期孤儿文件。快照、取消标识和核对记录保留审计；本批尚未实现完整正文/账号/备份删除，WAHA 自身文件也不在 A 的缓存清理范围。

新增迁移 **0011_waha_multitype_sending**，接在不变的 0010 后，增加五张发送表；不自动授权，不改旧接收/媒体记录。契约由源模型生成，不手改生成文件。不要为了升级删除 WhatsApp 会话卷。

## 一次性人工验收步骤

先完成自动检查，再用自己的账号、明确同意的测试聊天一次性验收。开发期间没有向真实号码发送。

1. 启动 Docker Desktop。已经使用团队本地工具初始化过的安装可运行下方命令；**不要为了升级再 init、provision 或 seed，不要创建第二套安装。**

   Windows 项目根目录：

   ```powershell
   $env:WAHA_SEND_ENABLED = 'true'
   $env:WAHA_MEDIA_ENABLED = 'true'
   .venv\Scripts\python.exe scripts/waha_team.py up
   ```

   macOS/Linux：

   ```bash
   WAHA_SEND_ENABLED=true WAHA_MEDIA_ENABLED=true .venv/bin/python scripts/waha_team.py up
   ```

   你的旧 `waha-a02` 安装沿用[媒体说明中的原数据库升级命令](role-a-media-ingestion.md)，迁移到 head 并 check，在原 ingress/media Compose 文件后加 `infra/waha-send.compose.yaml`，保留私有重启覆盖，仅重建 ingress/worker。不替换账号、数据库、绑定或会话卷。启用接口后仍需要页面明确授权才能发送。

   **只有需要视频时才选择 Chrome：**默认保留原 ARM/Chromium 环境。先暂停/撤销发送，再同时设置发送、媒体和 `WAHA_SEND_CHROME=true`，运行团队 `up`；工具会在 ARM 覆盖之后追加 `infra/waha-send-chrome.compose.yaml`，使用固定 Chrome 2026.9.1 的 linux/amd64 镜像。Intel 原生运行，Apple Silicon 使用模拟。仅只读查验了公开镜像清单，没有拉取/运行，模拟性能及手机表现待验收。旧安装可把这个文件加在所有覆盖之后，明确重建 WAHA 并保留会话卷；核对状态，仅确需时重新关联。代码不会自动切换镜像或浏览器。

2. 在 `apps/web` 启动真实前端。Windows：`$env:GIGMATE_API_URL='http://127.0.0.1:18702'; npm run dev`；Mac/Linux：`GIGMATE_API_URL=http://127.0.0.1:18702 npm run dev`。打开 Vite 提供的地址，登录，确认 WhatsApp 已连接，在消息区域选择测试会话；勾选并保存单独的发送授权。
3. 文字/链接：先保存草稿，手机此时应没有收到；核对最终内容再批准。检查手机、任务状态及只读回执，刷新页面不应再发。选一条已载入消息测试引用回复。改输入应重新核对新草稿。
4. 准备小型真实图片、音频、Ogg/Opus、MP4、WebP、PDF/TXT/CSV/Office 文件；每次上传一个，检查预览、附件名及 SHA256，再批准。检查手机图片/贴纸、音频附件与语音气泡、视频播放、说明及文件名。等待前一条回流并刷新上下文后再批准下一条。自动签名夹具不能代替播放验收。
5. 用虚构的地点、联系人、简单问题测试位置/名片/投票；检查选项及多选。对测试消息加回应，再留空移除。表情成功不应被描述成另一条已送达消息。
6. Agent 润色模式先粘贴虚构建议、修改并核对后发送；真实 B 模型另行联调。自动模式先批准一句固定回复政策，明确提交一次，核对手机、次数和任务记录；修改内容、撤销/用尽政策、使用旧版本都不应发出。此步骤不等于真实自主 Agent 已完成。
7. 保存草稿后，先收到/编辑/撤回一条相关消息，再试批准，旧草稿应失效。暂停接收、移出白名单或撤销发送授权时，未提交任务不能发出；明确恢复后才继续。任务已进入发送后，不能声称点击取消已撤回远端发送。
8. 超时、崩溃和丢失响应优先使用合成故障测试。遇到真实网络异常，先看原请求/任务及手机，不要因为查不到就重建请求。发送结果未知时，在实际核对后记录“可能已发送”，保留未知，只恢复后续独立任务。不要故意扰乱真实发送来制造重复。
9. E 补充独立 PostgreSQL 并发、HTTP/worker、Windows/Apple Silicon 与真实浏览器验收。当前开发使用合成传输、DOM 及 SQLite；没有证明真实手机、B 模型、PostgreSQL 锁、部署或生产验收。实际自动结果见[进度记录](progress.md)。
