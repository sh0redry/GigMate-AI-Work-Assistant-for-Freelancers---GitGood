# GigMate 前端使用手册

当前交付候选 · 2026-10-16。[English](../en/role-d-frontend-user-guide.md) · [本批验收与限制](role-d-final-acceptance.md)。

## 1 现在有哪些页面

本候选基于已合并 #26／#27 的 main `71de8d9`。现在只有一套业务服务：登录框留空，不显示公开密码，没有样例输入和环境切换。旧 `/environments/...` 书签会停在“旧入口已停用”，确认维护者配置的服务后再打开 `/`。这次没有删除、搬运既有业务或 WhatsApp 会话。

| 页面 | 可以做什么 |
| --- | --- |
| 业务工作台 | 搜索已有工单、查看原文版本、接受时间／只有日期／地址提议，并核对状态操作 |
| 新建工单 | 选择授权会话、填已知信息、勾客户原文、预览复核后，通过已合并的 C 接口保存 |
| 回复审批 | 核对正文／收件会话／原文／期限／版本，批准、拒绝／取消、重新提问、看历史 |
| 日历与待办 | 月历、全部安排、键盘选日期、全部工单待办、下载自己的正式预约 `.ics` |
| 人工复核 | 查看处理问题、区分旧轮次、读会话原文、打开相关工单 |
| WhatsApp 连接 | 连接、授权聊天、看消息／附件，使用另行明确授权的手动发送网关 |
| 功能与使用说明 | 看哪些可用、哪些还不能用、为什么不能用 |

空列表不一定是故障，也不表示 AI 已经理解了聊天。正式用户开通、真实模型启用和完整业务发送闭环仍需团队继续交付。

## 2 打开工作台

使用维护者给你的 GigMate 账号。它和 WhatsApp 是两套登录，不要填写 WhatsApp 手机密码。交付页面不会展示开发测试密码。

本机开发时，先启动已经配置好的后端，不要重置原数据库和会话。进入 `apps/web`，Mac／Linux：

```bash
GIGMATE_REAL_API_URL=http://127.0.0.1:18702 npm run dev
```

PowerShell：

```powershell
$env:GIGMATE_REAL_API_URL = 'http://127.0.0.1:18702'
npm run dev
```

端口以自己配置为准，浏览器打开终端打印的网址；后端要允许这个网页来源。旧“默认环境／隔离地址／别名”变量不再选择服务。交付网页统一请求同一网站的 `/api/v1`；开发代理只转发 GigMate 登录 cookie，不把连接器配置和密钥放入页面。测试资源由开发者在网页外另行准备，产品没有切换入口。

### 前端测试和构建

使用固定 Node 24.15.0、npm 11.12.1 和项目 Python 3.12.10。每个代码目录需有 `.venv/bin/python`（Mac／Linux）或 `.venv/Scripts/python.exe`（Windows），也可明确设置 `GIGMATE_TEST_PYTHON`。缺 Python 会说明原因并失败，不会跳过测试。

```bash
npm ci
npm run check:api
npm run format:check
npm run build
```

`build` 先测试再编译；`bundle` 只检查类型和编译，网页容器在检查格式后使用它。完整测试由提交前本机和 CI 执行，不把测试用 Python 装进交付网页容器。编译成功还不等于已经部署。

## 3 连接和管理聊天授权

在 WhatsApp 页按状态提示连接，再选择允许处理的聊天。“允许接收”与“允许发送”分别授权。手动发送要核对确切聊天和内容；服务接收不等于对方已收到或已读。结果未知时保留原编号核对，不能换编号重发。附件下载和来源核对已有入口，但本前端没有替 B 启用真实模型或扫描 PDF 识字。

## 4 业务工作台

先看摘要、状态、时间／地址以及每条依据的原文版本。一段聊天可以有多张工单；不知道的值就留缺失。客户“想这样改”、客户“明确同意”和商户“批准改动”是三件事。

时间或地址有提议时，先比较新旧值和原文，再明确勾选接受。“只有日期”仍是暂定；客户还没确认的推算值，即使你接受，也会保存为“待客户核实”，不会冒充客户已经同意。例如系统把“下星期六”换成某个日期，仍要让客户核实。旧版本、来源改变、撞期以及暂不支持的字段不能强行提交。

现在可以开始工单、标记等客户、完成或取消。先读清楚影响，再确认保存。完成／取消是终点：自动待办和未发送草稿会按规则收尾，历史保留；已经派发的 WhatsApp 请求不会因此撤回。

断网后没收到答复，不等于操作没成功。网页在提交前保存原编号和原内容；刷新、重新登录都不会自动重发。你有两个明确选项：核对后使用原编号、原内容、原版本重试；或点“只读核对已保存结果”，只查原操作在服务器上的保存记录，不执行操作。只有查到内容匹配的已保存记录，再勾选同意，才能点“结束已核对的原记录”。没查到时仍保留原记录，不能据此认定没有执行。浏览器禁止保存／清理失败时，先恢复存储；不能为了腾出按钮而手动删未知记录。这里不保存密码，原操作内容暂存在当前标签页。

## D-03：看清楚一条回复，再批准

完整核对正文、收件会话、来源版本、有效期，以及绑定／当前工单和会话版本；复核后再明确勾选批准。**已批准，尚未发送**只代表决定保存了。业务审批尚未自动接上 WhatsApp 发送，不要把旧审批复制到发送框，就假定它的来源和版本仍然有效。

拒绝／取消要写原因；重新提问只生成另一份待审批草稿，不发消息。页面会解释缺时间、缺地址、核实日期等追问原因，不只认识撞期；不认识的格式也会提示人工核对。历史保留关闭记录。旧入口如果还留有未知审批，本版会挡住新审批，让维护者先核对，不会静默搬到另一套服务重试。

## 5 新建工单和人工复核

选择已授权会话，填一个短摘要；不知道的时间／地址留空。填写了具体值，就勾选客户在哪条最新、未撤回的原文中说明它。商户自己的回复不出现在客户确认依据里。具体时间按香港时间填写；只有日期仍是暂定。已有未结束工单时，另开一单要再勾一次明确确认。改了内容或来源，旧复核就失效。

现在使用已合并 #26 的正式建单约定，前端类型从后端自动生成；本版服务端开放了手工建单、状态操作和地址确认。能力信息读取失败时仍关闭对应按钮。AI 自动建单、人工归单／延期跟进、业务审批接 WhatsApp 外发仍未交付。

人工复核页显示你已授权会话的处理记录和最新原文，不展示原始连接器数据包。旧轮次会明确标记。缺项会说明是在等客户提供、等核实还是等商户核对。人工归单／延期跟进还缺 B/C 的保存约定，所以不能保存。附件和部分结果到 WhatsApp 附件面板核对来源；模型文字不会因此自动变成已确认工单。

## 6 内部日历与手机导出

月历从星期一开始。点日期查看当天安排；方向键移动一天／一周，Home／End 到本周首尾；也可点今天、上个月／下个月。“全部安排”能看其他日期，也能选择显示已结束工单的历史。时刻按香港时间显示；只有日期的记录保留原日期与时区。全部工单待办可以筛选；后端还没有手动完成／编辑接口，所以目前只读。

**加入我的日历 (.ics)** 下载一条当前有效的正式预约。后端会重新检查是不是你的记录、时间和原文版本是否仍匹配；暂定、时间／来源不匹配、不可核对和已关闭工单不能导出。文件包含业务标题、准确时间、原时区说明和已有的已确认地址。手机会按自己设置的时区显示同一个时间点。下载文件含业务信息，请自己妥善保存。

在自己的日历里打开／导入文件。改期不会自动同步到 iPhone、Google 或 Outlook，需要手动更新／重新导入，并检查是否重复。这里没有 Google 登录、订阅或双向同步。真实 iPhone／Google／Outlook 的导入效果仍需独立设备验收。

## 7 安装、退出和常见问题

本版提供网页应用安装信息和图标；支持的浏览器可在 HTTPS 或本机地址下安装／添加到主屏幕。没有安装离线缓存或后台操作程序；断网不能办理业务。独立 exe、macOS 安装包、签名、更新和新设备安装尚未交付。网页装了快捷入口，后端、worker、数据库和 WAHA 仍要运行。

退出会清掉页面上的账号资料和输入，按账号保留尚待核对的原请求。登录过期就重新登录；读不到功能状态时相关按钮保持关闭；冲突或版本变化先刷新再核对；未知操作核对原编号。不要通过重置数据库／会话来解决网页问题。
