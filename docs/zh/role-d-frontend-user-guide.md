## 1 现在有哪些页面

登录前只有账号表单；输入为你配置的 **GigMate** 账号和密码，表单不预填，但开发登录页会显示公开测试账号 `merchant`、密码 `demo-only-change-me`。改过密码则使用实际配置。它不是 WhatsApp 手机登录。

登录后默认进入 **业务工作台**。隔离测试显示 **业务工作台** 和 **回复审批**，使用虚构数据；**WhatsApp 连接** 仅在真实连接环境（或发布部署）保留。隔离测试不会打开连接页，也不会发起该页的连接查询。移除了“D-01 演示预览”“模拟扫码成功”“模拟断线”和“工单回放”，无须找开关隐藏它们。开发测试仍使用虚构数据，但没有对应的用户操作入口。已经存在的测试数据库记录不会因移除按钮而删除。

大家能够连接 WAHA，是团队提供的进展；本次没有重新测试每个人的手机。连接与会话授权可用，不意味着自动建单、通用模型提取或发消息已完成。新建工单、状态修改和消息发送尚未开放。回复审批需要配套的 C 接口，它只保存你的决定，不给客户发送 WhatsApp 消息。

## 2 一键切换环境

网页顶部一直写明当前环境，并提供 **切换到真实连接／切换到隔离测试**。点击一次切换；不用停止前端或换代码。切换会重新打开登录页，清空页面账号、密码、业务详情和二维码；需要重新登录。两边的登录 Cookie 和待核对请求分别保存，不复制工单、聊天或授权。切换不是服务器退出，也不会取消已经提交的后台工作；正式退出请先用 **退出**。请求结果未知时回原环境核对，不另建请求。操作处理中禁止切换。

| 名称 | 页面里的数据 | 用途 |
| --- | --- | --- |
| **真实连接（本机开发）** | 你自己的 WAHA、本机数据库及已授权聊天；操作会影响这套记录 | 检查真实连接、会话授权和已有业务。它仍是开发环境，不是正式上线版本 |
| **隔离测试（虚构数据）** | 独立测试数据库的虚构工单、原文、日历和待办 | 练习与验收业务流程，不接入真实 WhatsApp 聊天 |

默认先打开隔离测试；网址中的 `/environments/real/` 或 `/environments/isolated/` 会保留选择，刷新仍在这一边。页面显示后端地址，读取失败会报错，不会自动换另一边顶替。

**首次准备仍需要两套后端。** 前端按钮只选请求送到哪里，不会创建数据库或启动服务。真实连接后端按[团队本机指南](role-a-team-local-development.md)准备；隔离后端按[开发入口](../en/getting-started.md)在独立数据库／schema 上启动、迁移、种虚构数据并运行确定性 worker。不要复用真实数据库／WAHA 会话。不同端口也可能误配到同一数据库，前端无法检查数据库内容；维护者必须保证隔离。配置会拒绝两边使用同一个本机端口。

在 **D 工作目录的 `apps/web`**，使用项目固定 Node 24.15.x/npm 11.12.x：

```bash
npm ci
npm run dev
```

默认真实后端 `http://127.0.0.1:18702`，隔离后端 `http://127.0.0.1:18000`。自定义端口只需启动时配置一次，随后用网页按钮切换：

```bash
GIGMATE_REAL_API_URL=http://127.0.0.1:18702 GIGMATE_ISOLATED_API_URL=http://127.0.0.1:18012 npm run dev
```

Windows PowerShell：

```powershell
npm ci
$env:GIGMATE_REAL_API_URL = "http://127.0.0.1:18702"
$env:GIGMATE_ISOLATED_API_URL = "http://127.0.0.1:18012"
npm run dev
```

18012 是本次预览隔离后端的端口，换电脑后使用你实际准备的端口。`GIGMATE_DEFAULT_ENV=real` 可改变首次默认选择。旧 `GIGMATE_API_URL` 现在仅作为**隔离后端地址**的兼容别名；原来用它指向 WAHA 的启动命令需要改为 `GIGMATE_REAL_API_URL`，避免贴错标签。更改地址后重启 Vite。两套后端的 `TRUSTED_ORIGINS` 都必须包含实际前端地址，例如 `http://127.0.0.1:5178`；前端不会跳过后端的来源／账号／CSRF 检查。

公开账号仅适用于默认开发安装；它不是 WAHA 管理密钥或手机密码。真实连接环境若配置了别的密码，以维护者配置为准。生产账号开通与部署仍待完成。`npm run build` 生成的发布版使用部署自己的 `/api`，不包含本机环境切换或开发密码提示；这两个入口仅在 Vite 开发模式提供。

开发者自检的特别情况：`python scripts/check_waha_setup.py --run --frontend` 会创建临时数据库和模拟 WhatsApp。页面标明 **合成连接自检（虚构数据）**，保留连接按钮是为了测试流程，二维码不能扫码；这里没有环境切换。工具自动设置 `GIGMATE_SYNTHETIC_PROVIDER=1`、明确的 18802 接入地址和 `GIGMATE_DEFAULT_ENV=real`，缺少明确地址／默认选择时 Vite 会拒绝启动，并关闭第二个代理。路径里的 `real` 只是选择连接流程，页面标签会说明资源都是虚构的。这与日常练习工单的隔离工作台不同，也不会连接真实手机。使用你自己的 WAHA 时不要设置这个自检开关。

### 前端测试和构建

前端测试会调用真正的合成自检 Python 函数。Mac／Linux 自动找当前项目的 `.venv/bin/python`，Windows 自动找 `.venv/Scripts/python.exe`；不用激活虚拟环境，也不依赖电脑上有没有叫 `python` 的全局命令。先按[项目安装步骤](../en/getting-started.md)准备虚拟环境。缺少它或指定路径不可用时，测试／构建会给出安装提示并明确失败，不偷偷跳过。

如果 D 的 worktree 工作目录没有自己的 `.venv`，可以明确使用主项目已有的 Python。Mac／Linux：`GIGMATE_TEST_PYTHON=/你的项目绝对路径/.venv/bin/python npm run build`；PowerShell：先设 `$env:GIGMATE_TEST_PYTHON='C:\你的项目\.venv\Scripts\python.exe'`，再执行 `npm run build`。把示例换成你实际的路径。这只是告诉测试去哪里找 Python，不是切换业务后端，也不是 WhatsApp 密码。CI 会创建固定 Python 3.12.10 的虚拟环境，分别在 Linux、Windows、Mac 检查前端。

旧 `GIGMATE_API_URL` 别名实际被用作隔离地址时，现在会打印明确警告。按上文换成 real／isolated 的明确变量；程序不能仅凭地址判断后端里是否真的都是虚构数据。

## 3 连接和管理聊天授权

这个页面仅在 **真实连接（本机开发）** 中提供。隔离测试里没有入口；需要连接时先点顶部环境切换，再重新登录。

1. 登录后打开 **WhatsApp 连接**。已有可靠的“已连接”状态时不用再扫码；还需明确保存要处理的聊天授权。
2. 没有连接记录：联系接入负责人检查该账号配置，再点 **刷新连接**。读取失败与没有配置是不同情况。
3. 需要关联时，按页面提供的 **开始连接** 或 **重新连接并获取二维码** 操作；手机 WhatsApp → 关联设备，扫描网页二维码。操作处理中等待结果。图显示出来不代表手机已关联，最后看新鲜的连接状态。
4. 二维码只暂存内存。获取后 30 秒隐藏，可见时约每 20 秒更新；服务可能更早换码。暂停、退出、离开或读取不可靠时隐藏。失败后先刷新状态，不复用旧图。
5. **载入会话与授权** 读取已保存选择。连接正常时点 **发现最近会话** 加载候选；它不是导入完整历史，每批最多 100 个，可明确载入更多。
6. 勾选后点 **保存会话授权** 才生效。搜索／个人聊天／群聊筛选／8、16、24 条分页只浏览已载入列表；其他页的勾选仍保留。**已授权** 筛选看已保存事实，不是尚未保存的勾选。
7. 取消勾选后保存减少授权；**撤销全部授权** 覆盖全部页。已有授权在断线、暂停或接入配置不可用时仍可读取、撤销。**放弃更改** 恢复保存事实。
8. 新候选通常十分钟过期；过期、另一窗口改过授权、读取失败或保存答复丢失时，先重新载入、核对，再操作。新发现可能刷新名称，但上游未提供昵称时不会保证恢复；号码标签会说明“未提供昵称”。
9. **暂停消息接收** 暂停接收；**恢复消息接收** 恢复已有授权，不保证补齐期间遗漏消息。授权用于读取／处理，不开启自动回复，也不直接确认工单。

操作答复丢失时，使用 **使用原请求核对**，保留原参数和请求编号。服务已报告 `result_unknown` 时，用 **核对未知操作（不重发）**；不要另点重连来替代核对。连接状态、消息处理服务和历史完整性分别检查。

故障已恢复后，核对时间范围，明确确认无需补导历史，再用 **清除已恢复故障**。只移除待处理标记，审计保留；未恢复故障不能清除。消息同步区域可以查看允许范围的时间线／同步进度，历史观测和附件信息不等于已整理成工单或解析了附件。

## 4 业务工作台

用 **搜索业务** 和 **工单状态** 找工单。筛选隐藏当前选择时，详情仍保持打开并有提示；不会偷偷切换业务。没有工单可能是正常状态，连接成功不会自动生成一张。页面说明自动／手动建单尚未开放，不提供假数据填充按钮。

详情显示当前版本、时间、地址和字段状态。未知地址仍显示 **未提供**。来源链接指向具体消息和修订；**显示会话** 可查看全部关联会话或一条。来源在其他会话被隐藏时，切回全部查看；某一修订未载入会提示需复核，不拿较新原文代替旧依据。

变更卡区分“谁提出”“顾客是否确认”“商户是否已批准”。目前只开放时间安排确认：点 **核对并确认安排**，比较新旧值、来源和版本，明确勾选，再点 **确认并同步安排**。

冲突、失效、来源缺失／撤回／归属不明、过期数据、已完成／取消工单和未支持字段都不可确认。刷新后提议或版本改变，旧核对失效，需要重新核对；不会把你对旧方案的勾选算成同意新方案。

成功后由后端同步正式工单、内部日历和准备待办，取消旧自动任务并保留历史；**不会给客户发送消息**，也不自动同步手机日历。**个人日历** 显示账号全部安排，标当前／其他工单和暂定／正式；时刻按香港时间，全天日期保留原时区。日期筛选包含跨夜安排。

**当前工单待办** 默认显示待处理和受阻；选 **全部（含历史）** 查看已完成／已取消项，查看截止时间、依赖和来源。**刷新业务数据** 重新读取。读取失败时旧数据明确标为过期，恢复成功前禁止确认；写入结果不确定时先刷新核对，不自动重发。

## 5 退出和常见问题

退出／登录过期清除当前页面账号数据、二维码和请求尝试记录；密码不保留在表单。完整刷新后需要重新登录，已保存授权和业务事实仍由后端保存。没有服务器确认退出的网络失败会提示，不假称已经退出。

| 现象 | 处理 |
| --- | --- |
| 登录不成功 | 核对 GigMate 账号、安装密码、前端所指后端与后端是否运行 |
| 看到旧演示入口 | 核对是不是 main／旧目录开的网页，停旧前端并从正确 D 目录启动 |
| 没有工单 | 核对当前账号；尚未开放建单，不要往真实环境种样例 |
| 显示旧连接／旧业务数据 | 服务恢复后刷新，先核对再操作 |
| 授权版本变化 | 重新载入，比较其他窗口的新状态后再保存 |
| 请求超时或结果未知 | 先核对服务器事实，不重复点击或换新请求编号 |
| 手机仍拒绝扫码 | 保留脱敏实际提示，由接入负责人排查；网页成功显示图不是手机成功证据 |

界面会随窄屏调整布局，可能需要上下滚动。真实手机和 Windows 原生运行仍需独立验收；本轮删除演示界面没有重做扫码或修改真实授权。

## 6 开发检查

在 `apps/web` 执行 `npm run check:api`、`npm run format:check`、`npm run build`；build 包含行为测试、类型和打包。开发测试仍保留固定回放逻辑和后端 `/replay`，用于隔离验证，不是普通用户入口。本轮未改后端源码、生成契约或迁移。通过忽略的本机 Compose 覆盖配置给现有 ingress API 加入本前端来源地址，并重启 API；重建时短暂选错数据库目标，已恢复到原 worker 使用的目标并复核健康／登录，已有连接／授权配置保持。不能仅凭移除按钮宣布项目已是最终成品。

## D-03：看清楚一条回复，再批准

进入 **回复审批**，选一份草稿。看完整正文、接收会话、原消息第几版、有效期，以及工单／聊天版本。先点 **核对这份草稿**，再勾选“我已核对”，才能批准。当前收件人显示系统里的会话编号；真正对应到 WhatsApp 收件人和发送还没接通。**已批准，尚未发送** 就像你签好了同意单，但信还没寄出。

拒绝或取消需要填写原因，并针对刚核对的那一份草稿。原文因撤权不可读时，可以关闭草稿，但不能批准或重新提问。草稿／原文更新后需要重新核对；过期、版本不一致、来源缺失／撤回时不能批准。选 **全部历史** 可查看已批准和关闭的记录；筛选不会偷偷换掉当前选择。

如果点击后断网，页面会保留“原请求”：原来想做什么、原来的版本和请求编号。刷新只看状态，不再批准一次。核对原草稿后，**核对后重试原请求** 使用同一编号／版本，可能完成第一次没送到服务器的同一个操作；不要另建一笔批准。核对时登录过期，并不能说明第一次没成功，所以原记录仍保留。退出、重新打开或换环境会清空页面，但不会删除这一账号／环境的待核对记录。记录坏了或浏览器不允许保存时，页面明确阻止新操作。

**重新生成待审批问题** 只产生另一份草稿，还要重新核对批准。C 后端“再次过期后重新提问”的问题已在 #22 修复并合并。本前端仍保守限制同一轮聊天、同一来源的重复再提问，是否放开这个界面限制可以以后调整。这里没有自动生成、修改正文、真实发送或外发核对功能。详细证据见 [D-03 验收](role-d-stage3-acceptance.md)。
