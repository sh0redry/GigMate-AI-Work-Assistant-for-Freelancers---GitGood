# 首期范围与产品边界

## 定位

中文产品名为跟單，工程名称使用 GigMate。产品协助商户和自由职业者跟进已经存在的 WhatsApp 业务，不建立人才配对或接单交易平台。原 README 的 GigPair 配对定位已停止沿用。

## 共同主线

已有 2026年10月7日 15时至16时预约。顾客提出改至10月8日同一时段并表示稍后提供地址，而该时段已有其他预约。系统要依次接收、归单、提出变更、检查冲突、准备澄清、商户批准发送、处理顾客回复、批准正式更新、调整待办/日历/旧提醒，并显示结果。

前端、AI 和后端使用 contracts 中同一组虚构输入。顾客只说“可以”不等于补齐地址；顾客提出时间也不等于商户同意。原安排在正式更新前保留，是否释放由商户决定。

| 优先级 | 交付范围 | 推进条件 |
| --- | --- | --- |
| P0 | 双方文字接入、连接状态、工单及来源、待确认队列、待办、内部日历、冲突检查、逐条审批代发 | 主线及异常场景验收 |
| P1 | 一种媒体、摘要、预授权提醒 | P0 通过后另定契约和测试 |
| 后续 | 外部日历、模板、周期服务、付款辅助、群聊 | 单独 ADR 与验收 |

不做：客户匹配、抽佣、资金托管、AI 定价议价、退款批准、法律判断、员工排班、采购库存、安全关键调度。

开发团队多人协作不等于产品内员工协作。首期支持个人经营者，保留多账号隔离，不增加组织管理复杂度。

## 启动门槛

真实自动接收是 P0 的独立要求。回放可以支撑开发，但不能替代真实接入证据。WAHA 版本、引擎、字段映射和收发能力尚未实测；只用于非关键测试账号。正式商用接入需要独立决策。

媒体、外部日历和付款模块不得阻塞首期。待验证收益包括减少整理时间和漏项，不能在 README 中写成已证明结果。
